# Spike: diarização do `elevenlabs/scribe-v2` no OpenRouter (2026-10-22)

## Decisão

**`diarize=true` funciona.** O endpoint devolve 200 com `speaker` / `speaker_label` por palavra. Portão da Task 0 (Step 6): **liberado**, a Task 1 pode seguir.

## Método

- Clipe sintético (`spikes/clip.ogg`, não versionado): 5 frases em português do Brasil alternando duas vozes do `espeak-ng` (`pt-br+m3` e `pt-br+f2`), pausas de 0,6 s, ~34 s, codificado com `ffmpeg -c:a libopus -b:a 32k`.
- Script: `spikes/diarize.sh [filename] [diarize|omit] [out.json]`.
- Requisição: `POST https://openrouter.ai/api/v1/audio/transcriptions`, multipart com `file`, `model=elevenlabs/scribe-v2`, `response_format=verbose_json`, `timestamp_granularities[]=word`, `language=pt`, `diarize=true`. A chave vai só no header `Authorization: Bearer $DAILY_TAKER_OP_KEY`.

## Resultados

| Teste | HTTP | Resultado |
|---|---|---|
| `diarize=true`, `filename=recording.ogg` (`audio/ogg`) | 200 | 2 locutores distintos (`speaker` 0 e 1) |
| `diarize=true`, `filename=recording.opus` (`audio/opus`) | 200 | Aceito; mesmos 2 locutores |
| Sem `diarize` | 200 | Aceito (**não** deu 400); palavras sem `speaker`/`speaker_label` |
| `GET /api/v1/key` com a chave válida | 200 | Endpoint de "Testar chave" |
| `GET /api/v1/key` com chave inválida | 401 | Distingue chave inválida |

Sequência de turnos reconstruída a partir de `speaker_label` (palavras consecutivas): `speaker_0` 21, `speaker_1` 16, `speaker_0` 12, `speaker_1` 13, `speaker_0` 13. Isso bate exatamente com as 5 frases alternadas, ou seja, a diarização acertou todas as trocas, mesmo com vozes sintéticas.

Idioma detectado: `por` (confiança 1). Custo da chamada de ~34 s: `usage.cost` ≈ US$ 0,0021.

## Formato real da resposta

`jq 'keys'`:

```json
["duration","language","language_confidence","segments","task","text","usage","words"]
```

`jq '.words[0]'` (com `diarize=true`):

```json
{"word":"Bom","start":0.02,"end":0.26,"speaker":0,"confidence":0.9989763259430114,"speaker_label":"speaker_0"}
```

Sem `diarize`, o item é `{"word","start","end","confidence"}` (sem `speaker`, `speaker_label`).

Observações sobre o formato:

- `words[]` **não tem o campo `type`** (a documentação cita `type`); só `word,start,end,confidence` mais `speaker` (inteiro) e `speaker_label` (`"speaker_N"`) quando há diarização. Não há itens de espaçamento/evento de áudio nesse clipe; o parser deve tolerar `type` ausente e, por precaução, ignorar itens com `type` diferente de `word` se ele aparecer.
- `segments` traz um único segmento (`id`, `start`, `end`, `text`) cobrindo o áudio inteiro, sem locutor: para agrupar por locutor, usar `words[]`.
- `usage` = `{"seconds": <duração>, "cost": <USD>}`.
- Os timestamps de `words[]` são em segundos (float).

## Resposta de `GET /api/v1/key`

Resposta 200 com objeto `data` contendo, entre outros: `label`, `limit`, `limit_remaining`, `usage`, `is_free_tier`, `rate_limit`. Basta o status 200 para validar a chave.

## Conclusões para a implementação

1. Usar `diarize=true` + `timestamp_granularities[]=word`; agrupar palavras consecutivas com o mesmo `speaker_label` em turnos.
2. Tanto `recording.ogg` quanto `recording.opus` são aceitos; pode-se enviar o arquivo gravado (Opus em Ogg) com `filename=recording.ogg`, `type=audio/ogg`.
3. Validar a chave com `GET https://openrouter.ai/api/v1/key` (200 = ok).
4. Ressalva: o teste usou vozes sintéticas, que são bem separáveis; com voz real em sala com ruído ou sobreposição a qualidade pode variar. Vale uma checagem com uma daily real no uso.
